# 스킬·에이전트 제작 체크리스트

이 프로젝트의 규정 원천은 두 곳뿐이다: **① 하네스 엔지니어링 책** (원문은 상위 허브 저장소 `reference/`에 있음, 이 저장소엔 없음), **② 앤트로픽 공식 문서**(code.claude.com/docs). 둘이 충돌하면 ②(공식 문서, 최신 사양)를 우선한다 — 책은 특정 시점의 설명이라 이후 사양이 바뀔 수 있기 때문이다.

> 이 파일은 상위 허브 저장소(거버넌스)의 `.claude/skills/skill-check/`에서 복사된 것입니다. 원본을 고치려면 거버넌스 저장소에서 고치고 여기도 다시 복사하세요.

## 절차

1. **먼저 필요성 판단**: 지금 만들려는 게 정말 새 파일이 필요한 반복 절차인가? 1회성이면 그냥 대화로 처리하고 스킬/에이전트로 승격하지 않는다 (하네스북 7장, Phase 4: 반복 관찰 후에만 승격).
2. **WHO vs HOW 판정**: "누가 맡을 역할"이면 에이전트(`.claude/agents/{name}.md`), "어떤 절차로 할지"면 스킬(`.claude/skills/{name}/SKILL.md`). 애매하면 하네스북 1-6절 참고.
3. 아래 표로 파일을 작성한다.
4. **공식 문서 교차검증**: WebFetch로 해당 문서를 다시 확인하고, 아래 표의 항목이 최신 사양과 맞는지 점검한다.
   - 에이전트: https://code.claude.com/docs/en/sub-agents
   - 스킬: https://code.claude.com/docs/en/skills
   - CLAUDE.md/메모리: https://code.claude.com/docs/en/memory
5. 결과를 사용자에게 보고할 때 이 체크리스트 표를 함께 제시한다 (✅/⚠️/❌).

## 에이전트 체크리스트 (`.claude/agents/{name}.md`)

| 항목 | 기준 |
|---|---|
| 위치 | `.claude/agents/{name}.md` (프로젝트) 또는 `~/.claude/agents/{name}.md` (전역) |
| `name` | 소문자+하이픈만, `:` 금지, 이 폴더 안에서 고유. **파일명이 name과 같아야 할 필요는 없음**(공식 문서 확정 — 하네스북 설명보다 최신) |
| `description` | 오케스트레이터/메인세션이 언제 위임할지 판단하는 근거 — 무엇을/어떤 기준으로/언제 3요소 포함 |
| `tools` | 필요한 도구만 나열(쉼표+공백 구분). 생략하면 전체 상속 — 도구 15개 이내 권장(하네스북: 많을수록 정확도 하락) |
| `model` | 명시 권장(재현성). 생략시 `inherit` |
| 본문 | 시스템 프롬프트. 최소 "핵심 역할"+"작업 원칙"+"품질 자체 검증"은 포함. 팀모드 아니면 "팀 통신 프로토콜" 생략 가능 |
| 금지 | `type:` 필드는 공식 스펙에 없음(문서화용으로만, 굳이 안 넣어도 됨) |

## 스킬 체크리스트 (`.claude/skills/{name}/SKILL.md`)

| 항목 | 기준 |
|---|---|
| 위치 | 반드시 **폴더 안에 대문자 `SKILL.md`**. 단일 파일(`skills/이름.md`)로 만들면 인식 자체가 안 됨 |
| `name` | 선택 필드. 있으면 목록에 표시되는 이름일 뿐이고, **호출 명령어(`/이름`)는 항상 폴더명에서 온다**(에이전트의 `name`과 역할이 다름 — 에이전트는 필수+식별자, 스킬은 선택+표시용) |
| `description` | 동사(뭘 하는지) → 트리거 상황(사용자가 실제 쓸 표현) → 경계조건(이 스킬이 아닌 경우) 3단계로. 250자 내외, 250자든 1536자든 첫 문장에 핵심 넣기 |
| 본문 | 500줄 넘으면 `references/`, `workflows/`로 분리(Progressive Disclosure). Why-First — 이유 없는 명령 나열 지양 |
| `allowed-tools` | 필요시만. 공식 스펙상 공백/쉼표 구분 문자열 또는 YAML 리스트 다 허용(하네스북은 공백만이라 했는데 최신 공식문서 기준으론 더 유연함) |
| `disable-model-invocation` | 부작용 있는 작업(발송·삭제 등)이면 `true`로 — 사용자가 직접 `/이름`으로만 호출 |
| 금지 | CLAUDE.md에 있는 내용(에이전트/스킬 목록, 디렉토리 구조)을 스킬 본문에 다시 베끼지 않기 — 링크로 가리키기 |

## 스킬 내부 세분화 — `workflows/`·`references/` (Progressive Disclosure)

**언제 만드나**: 개별 스킬의 SKILL.md 본문이 500줄에 근접/초과하거나, 조건부로만 필요한 상세지식(자주 안 쓰이는 참고자료)이 있을 때만. 스킬이 작고 단순하면 만들지 않는다 — 소속될 스킬이 아직 없는데 이 폴더만 미리 만들어두지 않는다(빈 폴더는 book의 Why-First 원칙에 위배 — 실체 없는 규칙은 지어낸 것이 됨).

**구조**: 둘 다 **그 스킬 폴더의 형제(sibling) 폴더**다 — 하나가 다른 하나 안에 들어가지 않는다.
```
.claude/skills/{그 스킬 이름}/
├── SKILL.md          ← 라우터: "어떤 모드/상황인가"만 판별
├── workflows/          ← "어떻게 하는가" 구체 절차 (모드별 파일)
│   └── 01-{모드명}.md
└── references/         ← 조건부 상세지식, 필요해질 때만 열림
    └── {주제}.md
```
- 근거(책, book-writer 스킬 실제 사례): "7 에이전트의 역할·호출 조건은 `references/agent-catalog.md` 참조... 사용자가 '통합본 만들어줘'라고 하면 compile 모드로 라우팅되고, 그 시점에야 `workflows/03-compile.md`가 컨텍스트에 올라갑니다."
- 근거(공식문서, code.claude.com/docs/en/skills): `workflows/`·`references/`라는 이름 자체는 공식 스펙에 없다 — "SKILL.md + 임의의 지원 파일들"만 규정하고 예시는 `reference.md`, `examples/`, `scripts/` 등 자유 명명. 즉 이 명칭은 책의 관례이며, 이 프로젝트에서는 그 관례를 따르기로 함(2026-08-20 확정).
